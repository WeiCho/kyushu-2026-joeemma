# 旅程手冊 UI 銜接優化設計

日期：2026-08-23
目標檔案：`template/itinerary.html.j2`（唯一需要改的檔；`行程表.html` 等產物由 `render.py` 重新產生，不入 git）

## 背景與問題

這頁是一份六天七人的九州旅程手冊，單頁、可離線（PWA）。使用者實際使用的第一情境是**旅途中、手機、隨手查**。

使用者提出的痛點有兩個，皆已用實測量化：

**一、視覺上是斷的，沒有一氣呵成。**
在 1707×781 的視窗以 100px 為間隔掃過全頁，量測「畫面上有多少比例被有內容（文字或控制項、有效不透明度 ≥0.15）的元素覆蓋」：

| 捲動位置 | 畫面有內容的比例 |
|---|---|
| scrollY 300 | 17.3% |
| scrollY 400 | 25.8% |
| scrollY 600–900 | 35.7% |
| 全頁中位數 | 54.7% |

手機（390×844，同源 iframe 量測）有 6 段完全無內容的垂直空白，最大一段 296px，佔畫面高度 46%。

成因是兩個機制疊加：

1. 章節留白 `--sec: clamp(88px,15vh,200px)`（`:64`），`.section` 只有上內距（`:300`）。
2. 捲動淡入（`:1436-1437`）：`fp = clamp01((vh − top) / (vh × 0.65))`，`--fade = clamp01((fp − 0.35) / 0.35)`。解出來是：章節頂端高於畫面 77.25% 時 `--fade` 為 0（完全透明），要降到 54.5% 才為 1。因此畫面底部固定有 22.75%（vh 781 時約 178px）是「有內容但看不見」。

**二、話題跳得硬，邏輯不連貫。**
現行動線為 封面 → 緊急 → 行程 → 花費 → 提醒 → 檢查。時態在跳（緊急／行程屬旅途中，花費／提醒／檢查屬出發前），且區與區之間沒有任何交代下一區為何是下一區的文字。

## 已確認不成立的假設

以下在規劃期被懷疑、實測後排除，**不列入本設計**：

- **點導覽跳轉不會落在空白或被頂列遮住。** 五個 hash 全數實測，落點 `top = 88px`，`scroll-padding-top: 5.5rem`(88px) 對上頂列高度 72.5–81px，留 7–15.5px 餘裕，落地後 `--fade` 皆為 1。`#day-3` 也能正確切到第三天再落地。
- **偵測器回報的 23 筆 `wide-tracking`** 全數落在中文標題的 `letter-spacing: .06em`，屬刻意排版，全數駁回。

## 範圍決定

使用者明確選擇：

- **不重排章節順序。** 只修過場與敘事感（規劃期的 A 方案「重排時序」已被否決）。
- **封面維持原樣。** 不加六天索引，不動標題與留白。
- **手機缺陷五項全部納入。**

## 設計

### 第一部分：過場機制

不新增任何元件，調整三處數值。（規劃期還有一條位移動畫，實作前取消，見 1.3。）

**1.1 淡入門檻**（`:1437`）

`clamp01((fp − 0.35) / 0.35)` → `clamp01((fp − 0.08) / 0.35)`

| | 現行 | 改後 |
|---|---|---|
| 開始出現（章節頂端位置） | 畫面 77.25% | 95% |
| 完全清晰 | 54.5% | 72% |
| 固定不可見的畫面底部 | 22.75%（≈178px @vh781） | 5%（≈39px） |

淡入區間長度維持 0.35 不變，浮現的質感不變，只是提早發生。

**1.2 章節留白**（`:64`）

`--sec: clamp(88px,15vh,200px)` → `clamp(72px,11vh,140px)`

`--sec` 同時被 `.section` 上內距（`:300`）、`:352` 的區塊內距、`:367` 的緊急區漸層停止點、`:386` 使用。

**其中 `:367` 必須先解耦。** 那是緊急區深→淺的漸層停止點（`calc(var(--sec) * .85)`），是全頁質感最好的一處轉場；若隨 `--sec` 一起縮短 30%，會從「感覺得到但看不見」變成看得見的硬邊。留白是節奏問題，漸層是質感問題，本來就不該共用同一個變數。

做法：新增 `--em-fade: 170px`（等於現行 `200 × .85` 的實際值），`:367` 改用它，與 `--sec` 完全脫鉤。其餘三處隨 `--sec` 縮小，比例關係不變。

**1.3 淡入帶位移 — 已取消，不做**

規劃期提議讓內容自下方 10px 移入。實作前取消，兩個理由：

1. 它是「每個章節都套同一個進場」，正是設計品質底線明列要避免的——動效應該是一個有作者性的時刻，不是每個交界重複一次。
2. 方向可能是反的。目標是**一氣呵成**，而在每個區塊交界加一次進場動畫，等於**強調**那個交界。

淡入維持純不透明度，那是這頁原本就有的語彙。

**實測結果**（1707×781，同一視窗、每 20px 取樣、有效不透明度 ≥0.15 才算有內容）：

| 位置 | 改前 | 改後 |
|---|---|---|
| 全頁最差點 | 17.3% | 28.2% |
| scrollY 300 | 17.7% | 29.3% |
| scrollY 400 | 26.2% | 33.5% |
| scrollY 600 | 36.7% | 36.6% |
| 全頁中位數 | 58.1% | 60.7% |

緊急區下緣漸層轉場經截圖確認完整，`--em-fade` 解耦成功。

**必須誠實記下的兩件事**，以免後人重做時被基線數字誤導：

1. **「最差 17.3%」這個數字有相當一部分是封面自己的留白。** scrollY 300 看到的是 100svh 封面的下半部（大標題置中，底下本來就空著），那是使用者明確要求維持原樣的設計，不是缺陷。拿它當問題陳述是誤導。
2. **淡入門檻的貢獻比推算的窄。** 理論上省下 178px，但章節頂端進畫面後前 127px 是內距（標題還在下面），真正「早看到字」的窗口只有章節頂端落在 562–654px 那一小段。中位數只前進 2.6 個百分點，真正吃掉中位數的是 `--sec`。

再往上推只能再砍留白，那會侵蝕這頁的呼吸感，不建議。

**未預先設定硬門檻。** 規劃期曾寫下「`scrollY 300` > 55%、中位數 > 70%」，但那兩個數字沒有依據，是看著基線憑感覺訂的。第一部分只有三處數值改動，做完立刻可量——正確做法是先量出實際落點，連同使用者自己捲過一遍的主觀判斷，再決定夠不夠、要不要再調。順不順最終只有使用者能判。

### 第二部分：敘事感

**2.1 銜接引子**

在**確實有邏輯關係**的兩處區尾加一行細線列，交代下一區為何是下一區，整行可點並跳至下一區：

- 行程 → 花費：**六天實際要花多少**
- 花費 → 提醒 · 檢查：**出發前還有事要確認**

採陳述句、不用提問句（「那麼，這六天要花多少？」在中文裡讀起來像行銷文案，與這頁「每天去哪、怎麼去、花多少，都在這一頁」的平實語氣不合），也不縮到「接著是錢」那種程度（省到沒有交代關係，等於退回原本的硬跳）。字數與頁面上其他灰字說明一致。

靠右對齊，0.8px `--line` 細線，套用導覽列既有的 `::after { right: 100% → 0 }` 下劃線動效。最後一區（檢查）不加引子，由 2.2 的頁尾收束承接。

**緊急 → 行程那一處刻意不放引子。** 那一跳本來就沒有邏輯關係（時態相同但主題無關），硬寫一行字去解釋，是在替一個不對的順序辯護，會掩蓋問題而不是解決。那一跳已經由全頁唯一的深→淺色彩轉場撐住，不需要文字。接得上的地方接，接不上的地方不硬掰。

因此引子只出現在淺色區，不需要深色變體樣式。

引子文案為靜態內容，寫在模板裡，不進 `trip.json`（它描述的是章節之間的關係，不是旅程資料）。

**2.2 頁尾收束**

頁面目前在「檢查」最後一個勾選框之後直接結束，像被裁掉。加一段結尾：0.8px 細線，其下一行 `2026.10.15 – 10.20 · 多三公斤回台`（日期用 `--latin`，標題用封面同一顆字、小級數）。日期與標題取自 `trip.range_label` 與 `trip.title`，不寫死。

**放在 `band-e` 之內**，吃該帶底色，只靠細線與字級差異和「檢查」區隔。不放到帶外的 `--paper` 上——那樣雖然與封面同底色、首尾呼應更成立，但等於為了修辭再切一次底色，而「視覺上是斷的」正是要修的問題本身，本末倒置。

列印時保留：紙本上它自然接在檢查清單之後，是合理的收尾。

**2.3 補上「行程」的說明行**

花費、提醒、檢查三區的 `h2` 底下都有一行 `.section-heading p` 灰字說明，只有行程沒有。補上：

> 一天一頁。用下方箭頭或鍵盤左右鍵翻日。

這同時把「一次只顯示一天」這個不可見的機制講出來——現行 5/6 的內容 `display:none`，鍵盤與瀏覽器搜尋皆無法觸及。

## 不做的事

- 不重排章節順序，不移動緊急區。
- 不改封面（標題、留白、浮卡位置皆不動）。
- 不改配色、字級、字重、線寬、圓角等既有設計語彙；所有新增元素一律使用 0.8px `--line`、4px 圓角、`--w` 600 字重與既有 `--ease`。
- 不改 `trip.json` 結構，不改 `render.py`，不改自動化流程。
- 不新增「一次看全部六天」的檢視模式（現行單日分頁維持不變）。
- **不加淡入位移動畫。** 見 1.3。
- **不加頂列進度線。** 規劃期曾提議加一條，後來砍掉：導覽列現有的五個標籤與 active 下劃線已經同時回答了「我在哪」與「還有幾區」，進度線多出來的資訊量趨近於零；而且頂列裡會出現兩條相距不到 10px 的 0.8px 線同時在動，違反這頁「唯一線寬、唯一功能色」的克制。使用者選的痛點也不包含「不知道還有幾區」——那是規劃時自行加進來的需求。

## 驗收

1. 全頁覆蓋率重掃完成，實際數字連同基線一併回報，由使用者判定是否足夠。
2. 五個 hash 跳轉落點仍正確（`top = 88px`，落地後 `--fade` 為 1），`#day-3` 仍能切日。
3. 主控台在 `行程表.html` 與 `?today=2026-10-16T14:30` 兩種載入下皆零錯誤零警告（現況即是，不得退步）。
4. 390px 下無橫向溢出（現況 `scrollWidth 372`，不得退步）。
5. 換日在三種路徑下皆正確：直接按箭頭、觸碰浮卡後按箭頭、今日模式載入後按一次箭頭。
6. 停用 JavaScript 時六天全部顯示、浮卡回到文流、所有新增元素不造成破版。
7. 列印輸出維持現況：六天全展開、提醒展開、深色區去墨。
8. `prefers-reduced-motion: reduce` 下無位移動畫且無殘留偏移。
9. 3.1、3.3、3.4 以實際量測確認達標，不以目視認定。

### 未能驗證（環境限制，非「已通過」）

- **手機覆蓋率掃描**：iframe 內的 `scrollTo` 未生效，320 個取樣點回傳同一個值，數據不可用。手機的無溢出與 44px 高度是另外量的，可信。
- **列印輸出**：只加了規則（`.handoff`、`.skip`、刪除線隱藏，已過行程還原 `--ink`），未實際列印預覽。
- **停用 JavaScript**：未實測。新增的 `.handoff`、`.coda`、`.skip` 都是純標記與 CSS，不依賴 JS。
- **`prefers-reduced-motion`**：本機為 `no-preference`，未實測 reduce 分支。1.3 位移已取消，新增元素只有 `.handoff` 底線與 `.skip` 位移兩個 transition。
- 桌機量測的視窗為 1707×781，非規劃時寫的 1440×900（`resize_window` 在此 Chrome 無效）。
